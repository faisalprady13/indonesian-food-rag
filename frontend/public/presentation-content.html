Project overview

Food RAG

A full-stack chatbot that lets you talk to a recipe database in plain language — search, ask questions, and manage favorites, powered by retrieval-augmented generation.

React + Spring Boot Postgres + pgvector OpenAI, bring-your-own-key JWT + OAuth2 Single Docker image

What it does

A cooking assistant that actually knows the recipe book

Instead of a generic chatbot, Food RAG grounds every answer in a real, searchable recipe collection stored in Postgres — so it can recommend, explain, and act on real dishes rather than inventing them.

💬

Chat with a recipe assistant

Ask for ideas in natural language — "something quick with chicken and rice" — and get real recipes from the database, not hallucinated ones.

🧠

Remembers what it just showed you

Say "save the second one" and it knows exactly which recipe you mean, because the app tracks the last list it displayed per conversation.

🗂️

Conversation history

Every chat is saved, renameable, and pinnable, with an auto-generated title — so past cooking ideas are easy to find again.

📖

Browse & favorite recipes

A paginated, sortable, searchable recipe list with autocomplete, plus a personal favorites collection — outside the chat, too.

🔐

Flexible sign-in

Email/password, or one-click Google and GitHub login, all backed by the same JWT-secured API.

🔑

Bring your own OpenAI key

Each user stores their own encrypted API key, so there's no shared LLM bill — usage and cost stay with whoever is chatting.

How it works

One request, five layers

The frontend is a single-page app that talks to one Spring Boot API. That API authenticates the request, retrieves relevant recipes from Postgres, and lets an LLM reason over them before answering.

Feature deep dive

The parts worth explaining in detail

01 Recipe RAG chat with tool calling

What

Users ask cooking questions in plain English and get answers grounded in the actual recipe catalog, not the model's imagination.

How

The question is embedded and matched against recipe vectors in pgvector. Spring AI's ChatClient exposes this search, an exact-title lookup, and favorites management as callable tools, and the model decides when to call them.

Why

Retrieval keeps answers factual, and tool calling lets the same conversational interface actually take action — search, look up, and save — instead of only describing what it would do.

02 Conversation context memory

What

Follow-ups like "save number 2" or "tell me more about the third one" work correctly, referring to whatever list was just shown.

How

Whenever a tool returns a numbered list, RecipeSelectionCacheService stores the position → recipe ID mapping against the conversation. A later tool call (getRecipeByListPosition, addFavoriteByListPosition) resolves the position server-side. This context row cascade-deletes with its conversation.

Why

LLMs are unreliable at recalling or inventing database IDs across turns. Resolving positions in the backend — rather than trusting the model to remember an ID — removes an entire class of "saved the wrong recipe" bugs.

03 Bring-your-own OpenAI key

What

Every user supplies and manages their own OpenAI API key from Settings; there is no app-wide OpenAI billing.

How

The key is encrypted at rest (ApiKeyEncryptionService). On each chat request, the backend decrypts it and uses ChatClientFactory to build a fresh, per-request OpenAI chat client and embedding model with that key.

Why

It removes a shared-cost/rate-limit bottleneck and keeps each user's usage isolated and billed to them, which matters for a project without a business model behind it.

04 Unified auth for local + social login

What

Users can sign up with email/password or log in instantly via Google or GitHub.

How

Spring Security runs a stateless filter chain: a custom JWT filter handles local sessions, while an OAuth2ProviderStrategy per provider normalizes Google/GitHub profile data into the same user model before issuing the same kind of JWT.

Why

Both login paths converge on one token format and one /api/** authorization rule, so the rest of the app never needs to know how a user signed in.

Technical decisions

Choices worth calling out

1

Postgres + pgvector over a separate vector database

Recipe rows and their embeddings live in the same database, so similarity search and relational queries (pagination, favorites, joins) share one store and one transaction boundary instead of two systems to keep in sync.

2

Server-side position resolution, not model memory

Rather than asking the LLM to track which recipe "number 2" refers to, the backend caches list positions per conversation. This trades a small amount of extra state for much more reliable multi-turn behavior.

3

Per-user, per-request LLM clients

A new ChatClient is built per chat request from the caller's decrypted key, instead of one shared client. This keeps API keys out of any singleton or cache and ties usage directly to the requesting user.

4

Database-backed chat memory

Conversation history for the LLM (DatabaseChatMemoryRepository) is persisted in Postgres via Spring AI's memory advisor, not kept in-process — so conversations survive restarts and scale beyond a single server instance.

5

Stateless JWT security throughout

SessionCreationPolicy.STATELESS plus a single JWT filter means the API never holds server-side session state, keeping the deployment simple to scale horizontally.

6

One container for frontend and backend

A multi-stage Docker build compiles the React app and copies its output into the Spring Boot jar's static resources. One image, one port, no CORS configuration to maintain between separate frontend/backend deployments.

Example flow

"Save the second one to my favorites"

A single follow-up message that touches almost every layer of the system — chat memory, vector search, tool calling, and position resolution.

1
Frontend

User sends a chat message

The Chat page posts the message to POST /api/recipe/ask with the current conversationId (or none, for a new chat).

2
API

Request is authenticated and routed

The JWT filter verifies the user, and RecipeChatService loads or creates the conversation and decrypts the user's stored OpenAI key.

3
LLM + tools

The model decides which tool to call

With the conversation ID passed in as tool context, the model calls getRecipeByListPosition(2) to resolve "the second one" from the last list it showed.

4
Backend logic

Position resolves to a real recipe

RecipeSelectionCacheService looks up position 2 for that conversation, returns the actual recipe ID, and the model then calls addFavoriteByListPosition(2) to save it.

5
Response

Confirmation flows back to the chat

The assistant's reply and the user's message are saved to Postgres, and the UI appends the confirmation — the recipe now shows up in Favorites.

Takeaways

What to remember

  • It's RAG, not just chatEvery recipe answer is grounded in real pgvector search results, not model imagination.
  • Tools do the actingSearch, lookup, and favorites are model-callable tools — the chat interface can take real actions on the database.
  • State lives in the backendPosition memory and chat history are server-persisted, so multi-turn conversations stay reliable across restarts.
